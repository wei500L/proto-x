# PROTO-X v0.1 机制对照 A/B：共同源端限速与多后台流

这19次受控测量仍未证明 PROTO-X 整体优于合理配置的 Hysteria2。六条后台下载时，优先调度在两个种子下都降低了 HTTP/echo p95，但 HTTP p99 和 SSE p99 反而提高。共同源端限速后，PX 的交互优势没有出现；Hy Brutal6 仍是必要的合理对照。

## 条件、版本与偏差

- 本地 Debian 13 arm64 VM 的真实包级 netem；两个vCPU，每个进程GOMAXPROCS=1。共同物理下行8／上行2 Mbps、名义RTT60ms、额外名义队列100ms，offload明确关闭。
- 每项独立3秒预热后测25秒；HTTP POST 5/s、持久echo最小间隔100ms、SSE源端50ms、请求超时3秒。所有应用实际经过SOCKS代理到同一个自有HTTPS源站，校验证书；HTTP使用keep-alive（cold_http=false），不是每请求都重建连接。种子103/109为发现数据；307未运行。
- A：每方向1%独立丢包、5ms抖动，一个源端按2.5Mbps应用字节预算发送的后台下载。此预算对每个协议相同，排除交互与代理开销，不是外层总速率上限。
- B：无配置随机丢包/抖动，六条不限速下载；有限队列仍可能发生拥塞丢弃。PX有8/2Mbps应用帧pacer；Hy Brutal6配置下行6／上行1.5Mbps及默认丢包补偿；BBR使用standard。不同总外层负载不能被隐去。
- PX使用冻结v0.1及quic-go v0.65.0默认 **Reno**。虽然构造函数名为NewCubicSender，[源码实际传入true // use Reno](https://github.com/quic-go/quic-go/blob/v0.65.0/internal/ackhandler/sent_packet_handler.go#L155-L163)。Xray 26.10.31使用VLESS+REALITY+Vision；Hysteria 2.13.0。完整SHA、Go build info与运行配置见各manifest。
- 续接摘要将B的第四个对照写成Xray，导致B103先运行Xray。澄清后B109按原定四变体运行，B103再补跑BBR。额外的Xray运行完整保留，并明确只有一个种子；BBR补跑时间偏离原随机调度，不能假装原顺序执行。
- 五个运行批次的全部五份二进制SHA、matrix.py和netlab.py SHA均一致；普通bin目录后续开发未影响冻结副本。未将新CC分支混入本研究。

## 完整性与限制

全部19项应用运行完成；HTTP 2374/2375，echo 4373/4389。未观测到HTTP或echo完整3秒超时、应用失败或拒绝；成功数与总数之差全部为测量末端截尾，原始事件保留。SSE无连接失败、序列/源端错误或异常终止，没有完整间隙超过1秒。A/FIFO/109出现一个254.7ms接收gap，对应源端间隔49.6ms；B/BBR/109出现一个277.0ms接收gap。全部SSE终端右截尾gap单独保留，不以缺少最终token掩盖中断。

HTTP p95/p99只统计成功请求，逐项都有分母；每项约125次HTTP、约500个SSE token，p99支撑有限。echo为闭环，慢协议会自然减少完成数量，不能当作相同开环到达负载。未合并不同种子的事件来制造更窄置信区间；当前重复数无法支持长期稳定性结论。19×25秒为多个独立测量窗，不等于单连接连续稳定运行475秒。

时延及SSE源端相对时间均用单调时钟。VM调度本身带来名义RTT以外的噪声；相同随机种子也不会让不同协议的同一业务消息逐个遭遇相同丢包。tc/nstat包含所有实验流量，其中namespace TCP重传计数还包含环回socket，不能当作QUIC重传率。这里没有测试俄罗斯现场、DPI识别、路径恢复、网络切换或长时间在线，不由这些数据推断这些能力。
