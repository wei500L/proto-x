# 稀疏 QUIC DATAGRAM 副本原型

基于 `5d80253`，研究分支 `research/hints`，仍使用上游 quic-go v0.65.0 的默认 Reno。它是独立的机制实验，未部署到测试 VPS，也没有预设性能优势。

## 机制

配置字段 `sparse_redundancy` 默认为 false。开启后，获得稀疏信用的 DATA 仍完整进入可靠 QUIC 流，再排队发送同字节、同偏移的 QUIC DATAGRAM 副本。单个副本 payload 最多 900 字节，大记录拆为几个带偏移副本；HELLO、OPEN、ACK、FIN、RESET 等控制记录不能通过这个通道执行。

副本在原件提交后等待 8 ms，以减少共用原包丢失位置的机会。它不保证两个副本在不同 QUIC 包中；拥塞、合包和底层调度仍决定实际包化。每会话副本队列最多 64 项，接收副本队列独立且最多 32 项；已经排队的可靠记录先处理。未来偏移副本直接丢弃，不新建乱序缓存。原可靠流仍负责最终填补缺口。

副本**同时消耗**独立的 10% 发送预算（上限 64 KiB/s）与原会话共享发送预算；未限速的实验配置仍保留 64 KiB/s 副本预算。预算按记录长度和相同的下层开销估计计费，并非精确的外层 wire-rate 上限。稀疏信用是按流字节活动推断，持续下载的初始字节也可能被选中，不能称为准确的 SSH / SSE 应用识别。

接收端只有已有、已打开的流可以接受有效副本，受相同偏移与消费窗口约束。副本可先行交付并被正常 ACK；之后到来的原件按偏移去重。这个 ACK 同样只意味着会话层收到了字节，不表示目标事务持久化或服务器崩溃后的恰好一次。

## 已修问题与限制

- 等待 8 ms 之后、每次预算等待之后重新检查副本是否已被确认，避免常见低 RTT 场景下明知无用仍扣主预算。确认与预算发放仍可发生并发竞态，计费可能保守地多扣，不能宣称零浪费。
- 副本接收与可靠接收队列已经分开。副本不能先填满可靠记录队列并阻塞 ACK/FIN；`NextFrame` 优先取已经排队的可靠记录。
- 40 ms 限制的是**调用 QUIC 之前的排队年龄**。上游 `SendDatagram` 没有 deadline API，内部 32 项发送队列可能阻塞；成功入队的副本也可能在拥塞后延迟发送。这一限制尚未解决，不能宣传为硬发送过期。
- 开关只控制本端发送；为了可接收兼容副本，QUIC 配置始终允许 DATAGRAM。无副本对照必须两端都设为 false。
- `HintSent` 表示成功提交 QUIC 队列；`HintDelivered` 表示副本先交付的字节。前者不是已在链路发送，后者不是“恢复丢包字节”。QUIC 打包器可能优先取 DATAGRAM，原件的 `Write` 返回也不代表它已经发包，因此即使无丢包副本也可能先到。
- 冻结试验中客户端退出日志有竞态，可能缺少最终计数；缺失不能按零处理。真实外层计数以实验室接口计数为依据。

独立评审见 [hints-review.md](hints-review.md)。开启功能需要同时评估交互延迟、SSE 间隔、失败、goodput 和总外层字节；只改善一个种子或一个分位数不足以推广。

## 实际检查

完整 `go test -race -count=1 -timeout=60s ./...` 与 `go vet ./...` 已通过。包括真正的 QUIC DATAGRAM 编解码与类型过滤、副本窗口/重叠去重、独立队列优先级，以及启用副本后的真实 QUIC→TLS 512 KiB 原 socket 恢复。后者使用单向 15 ms 的有界延迟路径，并要求切换前确有副本提交，避免回环 ACK 太快、实际零副本也通过。

另有 `TestHintAcknowledgedBeforeOriginalSurvivesCarrierReplacement`：记录级过滤器截留首个 2048 字节原件，注入其 900 字节副本，等待目标实际读取和正常 ACK，确认发送缓存从偏移 900 继续。替换承载后自动补发后缀，再重放完整原件，核验去重、单次目标 accept 与双向半关闭。定向 race 单次及连续 10 次通过。它明确是会话状态机检查，不是实际 QUIC 丢包测量。

## 复现

从主仓库的 `research/hints` 分支或归档 patch 创建隔离工作树，按主项目方式构建。双方在生成的私密 JSON 配置里设 `"sparse_redundancy": true` 即可；用于无副本对照时双方都设为 false，其余参数和二进制必须相同。

冻结实验 Linux arm64 二进制 SHA-256：
`0b42f0a8fc63165ed1e9e99d4eb650da6af4e3c097a2a08913fa6e50595d98fe`。

构建时使用 `-trimpath -ldflags '-s -w -X main.version=0.2.0-hints-experimental'`。
它基于未提交的工作树构建，Go 的 VCS 元数据记录 base revision 和 dirty=true；提交后直接构建会改变元数据。若要求同样构建状态，对 `5d80253` 应用归档 patch 后先不提交，再构建。使用同一个冻结二进制进行开/关对照不受这项元数据差异影响。
