# PROTO-X 实验报告

更新日期：2026-11-07。大部分比较和早期 VPS 结果使用冻结的 `0.1.0-experimental` 工作区实现；最早二进制没有记录 Git revision，不强行标为从某个提交构建。`5d80253` 是后续研究分支的代码基线。`0.1.1-experimental` 的心跳与退出清理改动单独列出，不追溯替换旧实验身份。以每个 run 的二进制 SHA、源码摘要、配置和原始事件为精确版本依据。

## 当前判断

已经做出可以实际运行的代理，以及跨承载保留原目标 socket 的恢复机制。**还没有证明 PROTO-X 整体强于 VLESS / Hysteria2。** 特别是 Hysteria2 Brutal 6/1.5 Mbps，在当前 8/2 Mbps、60 ms 名义 RTT、1% 双向丢包模型里，比第一版 PROTO-X 同时提供更低交互延迟和更高下载 goodput。

第一版的增量价值主要是应用会话与外层连接分离，已通过真实 SSH / SSE 续接验证。稀疏流调度有局部收益，也有尾部指标退化；应用限速本身带来的好处不能包装成新协议独有优势。拥塞控制和稀疏冗余仍在独立实验分支中检验。

## 方法和公平性

- 独立 Debian 13 arm64 VM、Linux 网络命名空间、同一双向 8/2 Mbps 瓶颈。healthy 为名义 RTT 60 ms；weak 为每方向 1% 随机丢包、5 ms 抖动。实际 `tc` 参数和计数差值随 run 保存。
- GSO/GRO/TSO、UDP segmentation 和相关 offload 显式关闭；不是在加密 TCP 字节流中随意丢字节。不同协议包数不同，同 seed 表示可复现的丢包模型，不代表每条业务遭遇完全相同的丢失位置。
- 常规筛选每项测量 25 秒，另加 3 秒预热；90 秒独立确认和真实 VPS 观察的时长分别列出。负载为 5 次/秒 HTTP POST、100 ms 间隔的持久回显、50 ms 源节奏 SSE，以及背景下载。HTTP 到达为开环；回显是单 outstanding 的闭环，不能用它掩盖停顿导致的少采样。
- 统计保留成功、失败、超时、拒绝和运行末尾截尾。延迟分位数只对成功样本计算，必须连同分母读取。SSE 单独记录跨连接间隔、序号错误、源端延迟、终端空白和长停顿。
- Xray v26.10.31，VLESS + REALITY + Vision；Hysteria v2.13.0，BBR standard / conservative 与 Brutal 8/2、6/1.5 Mbps。基线握手/下载有独立字节校验，版本与配置见 [baselines.md](baselines.md)。
- 稳定 PX 的 quic-go v0.65.0 默认是 **Reno**。PX 的共享应用 pacing、Hy Brutal 的发送控制、外层瓶颈是不同层；原始矩阵不能单独隔离它们。第二组实验对所有协议应用相同源端后台限速，另做 priority / FIFO 消融。
- 单轮和两个 seed 的点估计不提供统计显著性证明，短测 p99 尤其不稳定。不会把请求样本数当作独立网络实验重复次数。

## 第一组：同一瓶颈、一条不限速后台下载

关键点估计如下。完整八变体、配置失败及补跑记录保留在 [第一组分析](../results/discovery-20261106T224522Z/ANALYSIS.md)。

| 场景 / 实现 | HTTP p95，ms | Echo p95，ms | SSE 接收间隔 p99，ms | 下载 goodput，Mbps |
| --- | ---: | ---: | ---: | ---: |
| healthy / PX priority | 69.9 | 66.8 | 54.3 | 5.51 |
| healthy / VLESS REALITY Vision | 321.5 | 320.9 | 55.3 | 6.98 |
| healthy / Hy Brutal6 | 68.4 | 67.2 | 54.1 | 5.73 |
| weak / PX priority | 107.6 | 106.4 | 109.2 | 2.94 |
| weak / VLESS REALITY Vision | 178.2 | 87.5 | 67.6 | 2.47 |
| weak / Hy Brutal6 | 87.1 | 86.9 | 60.3 | 5.73 |

表中 PX / Hy 的 HTTP 各为 125/125 成功；VLESS healthy 为 124/125（1 个截尾），weak 为 125/125。PX / Hy 回显在 healthy 均为 248/249，在 weak 分别为 243/244、241/242；VLESS 回显分别为 84/85、226/227。所有差额均为运行末尾截尾，各项均无完整失败/超时，SSE 无序号错误或异常结束。VLESS healthy 的 echo p99 约 1621 ms，仅有 84 个成功样本，不能只用 p95 隐去这个尾部。

本组各实现的实际吞吐不同，VLESS healthy 的背景流量接近瓶颈，高延迟可能包含较多排队；不能把它直接说成 VLESS 固有开销。PX weak 的 HTTP p95 比它低，但 echo p95 / SSE p99 更差，尚非全面胜出。不能只选择排队严重的 Hy Brutal8 来宣称优势：降低它的速率预算后，Hy Brutal6 是这轮清晰的强基线。

SSE 接收间隔分位数不包含首 token 等待。例如 VLESS healthy 的首次 SSE 建立约 2457 ms、首 token 在测量开始后约 2460 ms；它后续约 55 ms 的间隔 p99 不能表示启动很快。完整建立与末端空白事件保留在原始数据。

较激进的 Hy BBR standard 在 weak 中获得更高 goodput（约 7.18 Mbps），同时 HTTP p95 约 195.6 ms；保守 BBR 可降低部分尾延迟。该现象说明应比较延迟、速度与外层开销的取舍曲线，不能只挑一个峰值。

两次原始 Brutal6 配置使用了该版本不接受的 `1.5 mbps` 字符串，被解析器拒绝；改为等值 `1500 kbps` 后补跑。原始失败保留，既没有删除，也没有冒充代理请求失败。更早的 smoke 有时钟与 offload 口径问题，未纳入上述性能结论。

## 第二组：共同源端限速与多后台消融

实验使用未用于第一组的 seeds 103、109。共同 2.5 Mbps 限速作用于受控源端后台下载，逐协议一致；它不包括交互数据和传输头部，不能称为整个协议的相同 wire-rate 上限。

在共同源端限速的 weak 场景，PX priority 两个 seed 的 HTTP p95 都比 FIFO 高（111.2 vs 105.2 ms；129.6 vs 113.8 ms）；echo p95 略低（102.4 vs 111.2 ms；104.1 vs 108.6 ms）。Hy Brutal6 在两个 seed 的 HTTP / echo p95 更低。现有调度器的增量不能据此称为全面改善。

在 healthy、六条不限速后台下载时，PX priority 相对 FIFO 的 HTTP p95 从约 101 ms 降到约 86 ms；echo p95 也改善。但 SSE p99 与 HTTP p99 反向退化，说明高低优先级、信用补充及底层 QUIC 排队之间仍需改进。必须保留这些退化指标。

完整目录、各 run 的分母与逐 seed 对照见 [第二组分析](../results/mechanism-ab-v01-20261106/ANALYSIS.md)。共 19 次运行，HTTP 2374/2375（1 个截尾），echo 4373/4389（16 个截尾），没有完整失败或超时。多后台组额外运行的一项 Xray 数据保留；原定 BBR standard 已补齐，不能靠删除误跑数据使设计看起来从未偏离。

## 拥塞控制与窗口诊断

在相同旧 QUIC fork 内比较 Reno、Hysteria BBR standard 和 Brutal6/1.5，训练 seeds 211/223 的结果没有支持直接替换主线拥塞控制。BBR/Brutal 将下载 goodput 提高到约 3.52–3.53 Mbps，但 HTTP / echo p95 多数增至约 145–153 ms；正式 Hysteria Brutal6 的 HTTP p95 为 85.4/94.1 ms、echo 约 85 ms、goodput 约 5.73 Mbps。完整数值和两种实现身份的区别见 [CC 筛选](../results/cc-screening-20261106/ANALYSIS.md)。

该轮 HTTP 1250/1250，echo 2389/2397，其余 8 个是测试结束截尾；无完整失败/超时。复用 Hysteria 的 CC 不是原创算法；稳定版与旧 fork 之间的差异也不能全部归因于 CC。

[窗口诊断](../results/cc-window-diagnostic-20261106/ANALYSIS.md)固定同一 fork、Brutal6、seed 227，只改变两端信用窗口：64/128/256 KiB 对应约 3.634/5.165/5.505 Mbps，HTTP p95 约 154–160 ms，没有同时改善交互尾部。更大窗口能释放吞吐，也增加每流缓存，故部署默认仍为 64 KiB。

旧 fork 缺少后续上游修复，且迁移时会重置自定义 CC，没有部署到 VPS。另完成官方 quic-go v0.65.0 上的小型 CC 扩展研究：更新在事件循环串行处理、迁移后保留 controller factory、MTU 降低时重建 CC；对应迁移、NAT、MTU 和 QUIC→TLS 字节恢复检查见研究归档。它解决研究基础设施的正确性问题，**没有相应的性能优越性实测**，仍独立于部署主线。

## 稀疏副本：有独立验证的局部增量

研究分支 `research/hints` 在可靠 DATA 原件之外，延迟 8 ms 提交不超过 900 B 的 QUIC DATAGRAM 副本；副本占用相同总发送预算，另受 10% / 64 KiB/s 预算限制，按原有偏移去重。它基于官方 quic-go v0.65.0，并保留可靠原件、ACK、窗口与原 socket 恢复语义。[源码、评审和复现](../research/README.md)已归档；未合并为 VPS 默认实现。

[15 项筛选](../results/hint-screening-20261106/ANALYSIS.md)使用 seeds 311/313 及预先追加的 317：不限速背景流量下有退化，共同源端 2.5 Mbps 时两个 seed 的 HTTP / echo p95 与 SSE p99 均改善；5% 丢包、源端 1 Mbps 的筛选中出现值得复核的 echo / HTTP p95 信号。保留全部不利结果，没有按指标选择性删除运行。

之后释放此前未使用的 seed 307，[预声明](../results/hint-confirmation-s307-20261107/PREDECLARED.json)固定参数与判据，运行 off / on / HyBrutal6 各一次 90 秒、另加 3 秒预热。条件为名义 RTT 60 ms、每方向 5% 随机丢包与 5 ms 抖动、物理 8/2 Mbps、共同背景源端 1 Mbps。**主判据是 on 相对同一二进制的 off 同时降低 HTTP 与 echo p95，独立验证通过。** 这不是统计显著性检验，三个运行不能当作大量独立网络重复。

| 独立验证变体 | HTTP p50 / p95 / p99，ms | Echo p50 / p95 / p99，ms | SSE 间隔 p99，ms | >250 ms 完整间隔 | goodput，Mbps | 双向 qdisc，Mbps |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| PX 副本关 | 96.0 / 201.3 / 239.4 | 86.9 / 185.3 / 268.1 | 161.0 | 2 | 0.968 | 1.326 |
| PX 副本开 | 93.7 / 164.5 / 213.0 | 86.7 / 145.4 / 206.6 | 154.0 | 1 | 0.956 | 1.477 |
| Hy Brutal6 | 67.7 / 167.0 / 240.9 | 67.4 / 174.0 / 243.3 | 144.6 | 0 | 0.967 | 1.188 |

on 相对 off 的 HTTP p95 下降 18.3%、echo p95 下降 21.6%，代价是双向 qdisc 字节增加 11.4%、goodput 下降 1.2%。相对 Hy，echo p95 低 16.4%，HTTP p95 仅低 1.5%；中位延迟、SSE p99 和完整长间隔数量仍更差，外层字节约多 24.4%。这里的共同预算是背景源应用预算，不是三种代理总 wire bytes 相等；qdisc 包含交互、控制与重传，不是纯副本字节。

每个变体 HTTP 450/450；echo 分别为 776/777、838/839、819/820，三个差额均为末端截尾。没有应用失败、完整超时、拒绝、SSE 序号/源错误、异常结束或 >1 秒间隔；闭环 echo 的完成数不同，停顿会降低它的采样频率。资源、原始事件复核、完整分位数和来源在[独立验证报告](../results/hint-confirmation-s307-20261107/ANALYSIS.md)。

这支持“低背景流量、较高随机丢包时，稀疏副本可以减少部分交互尾部”这一有限结论。40 ms 过期检查只发生在提交 QUIC 前；库内部 DATAGRAM 队列尚无硬截止时间，客户端冻结版本的退出计数日志也可能缺失。`HintSent` 是提交数，`HintDelivered` 是副本先交付字节，都不能直接称为丢包恢复量。主线修复了退出顺序，但没有把这些历史缺失追补为零。

## 真实测试 VPS

部署环境实查为 Debian 13 amd64、1 vCPU、128 MiB RAM + 128 MiB swap、约 1 GiB 磁盘、NAT 网络、MTU 1500。没有 `CAP_NET_ADMIN` / `CAP_NET_RAW`，因此没有在该 VPS 伪称执行 netem 或 tcpdump。故障通过客户端本地有界 UDP relay 注入，只影响本次试验；测试期间保留管理 SSH 和原有参考服务。

客户端在当前 macOS 网络直接连接授权 VPS。地理时区不是网络测量，不能据此宣称代表莫斯科家宽或俄罗斯移动网络。

| --- | ---: | ---: | ---: | --- |
| [45 秒混合负载](../results/vps-20261107/native-quic.summary.json) | 225 / 225 | 440 / 441 | 898 / 1 | HTTP p95 93.98 ms，echo p95 75.96 ms；5.57 Mbps 下载。 |

这三次回显分母各含 1 个测试结束截尾，无完整失败或 3 秒超时；SSE 均无序号/源错误或异常结束。黑洞试验并非无感：HTTP p95 1376.93 ms、SSE 最大间隔 2736.06 ms，出现 1 个超过 1 秒的 SSE 间隔。它证明原连接续接，不能用正常阶段的平均值隐藏故障期间的等待。

源端口更换试验的 HTTP p95 为 159.03 ms、SSE 最大间隔 356.09 ms；不是零延迟迁移。45 秒试验 cgroup 内存峰值为 14,610,432 bytes（约 13.94 MiB）、没有服务重启。上述短测没有给出日级可靠性。

### 10 分钟观察：不断新建流、持续 SSE 与受限下载

[原始统计](../results/vps-soak-20261107/bench.summary.json)与[资源记录](../results/vps-soak-20261107/soak-summary.json)已经完成，实际 benchmark 为 600.001 秒，不能外推为已运行一整天。

- 3000/3000 个 **cold HTTP POST** 成功，每次建立新的代理流；p95 295.75 ms、p99 581.95 ms。这个负载包含连接建立，与 45 秒复用 HTTP 的表格不同，不能直接解释为同一条件下的时延趋势。
- 5610/5610 次持久回显成功，p95 135.42 ms、p99 252.90 ms，最长 1060.80 ms。
- SSE 11995 个 token、始终 1 个连接，无序号错误、源错误或异常结束；53 个接收间隔超过 250 ms，没有超过 1 秒的完整或截尾间隔，最大完整间隔 899.63 ms。这仍是可以改进的短暂停顿，不能描述为“完全没有卡顿”。
- 背景源端设置 2.5 Mbps，实际校验下载 goodput 2.225 Mbps；运行末尾的下载流按截尾计。
- 117/117 次资源采样有效，服务 PID 始终相同、自动重启次数 0；采样内存最高 12,443,648 bytes（11.87 MiB），内核记录峰值 13,058,048 bytes（12.45 MiB），约 13.58% 单核平均 CPU。资源采样从独立管理 SSH 读取，没有在期间修改网络或重启服务。

这提供了持续新建流时的一段实际资源与稳定性证据，没有给出多日泄漏上界、移动端电量或未知负载容量保证。

前面的黑洞和源端口变更试验在故障前重启实验服务以清理前次会话，**没有在故障期间重启服务**。SSH 220 行来自一个认证后的 SSH 进程及同一条代理流；SSE 的连接数独立核验为 1。恢复能力依赖原服务端进程、目标 socket 与缓存仍存活。

### 服务进程重启：明确的恢复边界

[重启故障](../results/vps-restart-20261107/fault-summary.json)刻意在负载中重启 PROTO-X 服务。旧 SSH 只收到 56/220 行并以 255 退出，不能恢复；HTTP 147/150 成功、3 个明确失败，之后新请求恢复。echo 为 276 成功、3 失败、1 个末端截尾。SSE 收到 578 个 token、使用 2 个连接，记录到 1 次异常结束和 1 次连接失败，最大跨连接间隔约 899 ms。完整分母见 [统计](../results/vps-restart-20261107/bench.summary.json)。

这些失败没有从延迟统计的分母中隐藏。共享认证或恢复票据无法重建死进程的原目标 socket；当前实现需要应用重新建立连接，不重放旧应用请求。

### 空闲开销与 v0.1.1 修订

[v0.1 的 60.213 秒观察](../results/vps-idle-20261107/idle-summary.json)没有打开应用流，仅保留 1 条 QUIC 承载。双向共 850 个 UDP 包、58,899 字节 payload，合计约 978 B/s；按每包增加 28 字节估算 IPv4+UDP，约 1373 B/s。这包含连接建立与关闭，不是纯稳态、二层账单或移动无线能耗。

据此，v0.1.1 去掉默认服务端的重复主动 PING，保留客户端 PING、服务端 PONG、原失联阈值和自适应模式所需的服务端 RTT 探测。若服务端已静默半个失联窗口，仍会主动补探测，兼容心跳设置较慢的客户端。另修复客户端返回早于管理循环和会话清理的竞态，并使未完成的 HELLO/WELCOME 握手响应取消。该调整是通用控制开销优化，不是 PROTO-X 独有的延迟机制。新版本的真实字节与故障复测单独记录，不将旧版本观察当作新版本结果。

[新版 60.214 秒实测](../results/vps-idle-v011-20261107/idle-summary.json)仍为 0 应用流、1 条 QUIC 承载：双向 425 包、37,931 字节 payload，约 630 B/s；估算 IPv4+UDP 约 828 B/s，比前次减少 39.7%。包率约减半。[比较口径](../results/vps-idle-v011-20261107/comparison.json)保留原数值和两个独立时段；没有把它当作电量实测或精确稳态保证。

[新版 UDP 黑洞复测](../results/vps-blackhole-v011-repair-20261107/fault-summary.json)中，原 SSH 220/220 行、顺序正确，最长间隔 2708.73 ms；HTTP 150/150，echo 257 成功 + 1 个结束截尾。SSE 598 个 token / 1 个连接，无序号错误或异常结束，最大间隔 2608.97 ms，2 个 >250 ms 间隔中有 1 个 >1 秒。降低空闲开销后本次恢复仍有效，但依然有约 2.7 秒可感知暂停。

## 成本、安全和暂未验证的能力

- 可靠会话层增加记录头、ACK、缓存和处理；其开销与底层 QUIC/TLS 重传叠加。链路计数包含真实包头与交互业务，不把 bulk goodput 与总 wire bytes 的比值直接当作纯协议头部比例。
- 默认 `2 sessions × 32 flows × 64 KiB × 2 directions` 约为 8 MiB 应用有效缓冲容量；它不包括切片容量、QUIC 窗口、运行时、socket 等，也不是 RSS 上限。
- 心跳带来持续空闲成本；没有“零待机流量”主张。v0.1.1 降低主动探测数量，但不改变 2 秒失联阈值。冷建 TLS 备用也会增加故障期间的应用等待。
- TLS 回退解决承载可达性，仍有 TCP 队头阻塞。没有网站拟态、ECH、抗分类器数据集或主动探测回落证明。当前自定义 ALPN/SNI 容易被规则识别。
- 标准密码与十项认证/边界检查已运行；没有生产安全认证或大规模抗 DoS 证明。[安全评审](security-review.md) 记录已修复缺陷和具体范围。
- 记录解码器另完成 [60 秒、双 worker fuzz](../results/verification-20261107/wire-fuzz.json)，约 1408 万次输入执行，无失败；这不包含完整协议状态机 fuzz。
- 尚未进行多日连接观察、真实俄罗斯移动网络切换、电量测量、跨机 socket 存活或全球路径推断。实验分支不会自动继承主分支的部署和安全检查结论。

## 最值得继续的方向

目前优先保留的是同进程跨承载恢复，以及稀疏副本在固定低背景预算下的局部增量。下一轮应先限制 QUIC 内部过期副本的排队，检验能否在保持交互收益时减少额外字节，再用新的独立网络种子评估突发丢包、容量骤降和不同源速率。继续比较完整延迟/速度/成本取舍，不能只追逐一个 p95。

seed 307 已使用并冻结，不能再次作为未见验证集。v0.1.1 与副本/新 CC 的组合需要重新检查和测量，不能把独立分支的优点相加。多日观察、真实俄罗斯移动切换、抗识别和跨服务器存活仍未验证；下一轮保留失败与参数选择记录，不将未完成的计划写成成果。
