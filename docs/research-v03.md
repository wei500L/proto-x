## 3.23 秒能解释到什么程度

旧 VPS 记录中，SSH 最大相邻接收间隔为 3227.27 ms；客户端 H3 detach 到 H2 attach 是 498.371 ms。旧日志没有探针进展、故障注入与客户端统一的单调时钟，也没有 qlog，不能把其余时间精确分配给 PTO、锁或认证。

源码证明 v0.2 会话管理器每 500 ms 检查一次 `lastRX`，静默超过 2000 ms 后主动 `Drop`，然后客户端额外等待 100 ms 再拨下一个端点。H2 的 TCP/TLS/ECH、HTTP 认证与 HELLO/WELCOME、每条 Flow 的 OPEN/OPENED/偏移对齐及首个数据返回还各有成本。2 秒阈值加至多一个检查周期是一条明确的策略等待路径；不能据此声称旧 3.23 秒全由它造成。

原 SSE 设置的是 3 秒 inactivity deadline，HTTP 也是 3 秒请求期限，SSH 仍保持目标连接。服务端能保留 socket，不会撤销应用已经超时关闭的 socket。恢复实验现在同时记录应用事件序号、原目标连接 ID、双方会话事件和接收端故障规则，以判断是原流继续、外层恢复还是应用重连。

继承的 Linux pilot 在 OUTPUT 丢弃 UDP，可能让本地 `send` 返回错误，产生约 49 ms 的立即断链，不能代表静默黑洞。本轮工具改到对端 INPUT 丢弃，保存 nft 命中计数。旧结果保留但不参与新静默黑洞的收益结论。loopback 工具的 TCP chunk 延迟也不当作真实 TCP/netem 结果。

## 机制一：按双向进展和候选证据恢复

实现：[`path.go`](../internal/session/path.go)、[`delivery.go`](../internal/session/delivery.go)、[`client_recovery.go`](../internal/app/client_recovery.go)。状态包括 32 个近期匹配 PONG 的应用层 RTT、最老未答探针年龄、可因果匹配的业务进展、会话代次、应用需求和候选连接状态。下行 DATA 不证明上行仍可用，因此不能用它抹掉未答 PING。

设近期 RTT 中位数为 `q50`、90 分位数为 `q90`，耐心窗口为：

```
T = max(150ms, q90 + max(25ms, 4*(q90-q50)))
```

至少有 3 个样本且有未完成 OPEN、未确认数据或近期流式业务时才提前行动。探针年龄超过 T，可准备一个备用 HTTP 连接；准备完成要求 TLS/ECH 验证成功，但不发送代理 HELLO，因此不替换服务端会话。原路径匹配 PONG 或足够新鲜的因果业务确认到达则撤销准备。探针年龄超过 2T，候选可用且代次、进展证据未改变，才激活恢复。正常高 RTT 获得更长窗口，不把“低 RTT 下固定 400 ms”硬套到所有路径。

这是一个可解释的双阶段启发式策略，不是具有已证明最优误判概率的序贯检验。T 的保守估计可能在抖动后延长恢复；准备会暴露额外连接并花费握手字节；备用端点失败、长时间全路径断开或服务端固定静默阈值仍会限制它。客户端按需求加快探针，最快约 100 ms；空闲时保留原心跳频率。探针绕过应用 DATA pacing，线速评估必须计入；本轮 netlab 的 tc 同时约束两条承载的所有 IP 包。

首轮发现纯 32 样本窗口与探针频率相互影响：早期的 205–332 ms 排队样本让 T 达到 620 ms，探针因此变慢，旧样本又更迟被替换；故障前已连续约 3.9 秒保持 101–107 ms，也未消除这种影响。

尝试过时间新鲜度窗口：用原历史 RTT 中位数定义 `H=max(2s,8×medianRTT)`，筛选最后一次有效 PONG 前 H 内的样本，并至少保留最近 3 条。故障期间不自行淘汰证据。它能消除构造轨迹的旧峰，但在 18 次真实网络仿真消融中，黑洞没有稳定总体改善，短暂 pulse 还出现 1/2 误切换；纯计数窗口该小样本为 0/2。因此最终配置默认 `recovery_count_history=true`；显式 false 仅用于继续研究，不把负面实验包装成默认收益。

### 业务确认的因果进展

一次 age-no-prepare 实验在故障注入前就误切到了 H2：最老 PING 已等待约 304 ms，但 echo 在切换前约 104–112 ms 完成了一个约 107 ms 的往返，且整个往返发生在该 PING 发出之后。HTTP 也在该窗口完成，SSE 每约 50 ms 持续。这是不同 H3 流进展不一致的具体证据；控制探针的等待不能直接代表所有业务都失去双向连通性。

新机制利用代理已经维护的累计字节偏移，不发送额外业务副本。每条 Flow 保存最多 8 个新 DATA 末尾偏移与发送起始时间，位置在 pacing 和代次检查之后、实际 Send 之前。当前代次有效 ACK 推进累计偏移并覆盖某个新标记，才证明该发送之后有过往返；取最新被确认的**发送时间**，不用 ACK 到达时间冒充新鲜进展。最初一次 OPEN/OPENED 也可提供证据。每次换代以历史最高尝试发送偏移建立边界，重放旧数据与重发 OPEN 都不能作为新路径的业务探针；重复、无效 ACK 和单向 DATA 不增加证据。

有效探针年龄为 `now-max(oldest_unanswered_ping, latest_proven_send)`。只有该确认对应的发送晚于最老探针，且距当前不超过 T，才能撤销备用准备。迟到的确认可以保守地缩小年龄下界，但不会触发撤销后的冷却期。PONG 仍单独用于 RTT 分布估计，不把业务排队或 ACK 合并时间伪造成传输 RTT。消融 `recovery_probe_only=true` 完全关闭这项业务证据。

这是一种会话层健康判断，不声明丢失 QUIC 包，也不改变拥塞控制。每条 Flow 只多 8 个标记，ACK 匹配 O(8)，历史估计最多 O(32 log 32)。它在有新请求或新上行数据且反馈及时的场景提供证据；纯 SSE 下行、窗口堵满、持续高 RTT 或反馈稀疏时，仍依赖探针。环形历史覆盖、保守重放边界会漏掉可用证据，不能据此声称没有误判。
消融 `recovery_no_prepare=true` 保留检测逻辑，在确认后冷拨号；`recovery_mode=legacy` 保留 v0.2 的检测行为。它们不是仅凭开关存在就算贡献，收益与失败由真实包网络实验比较。

## 恢复的安全与连续性边界

TLS exporter 认证、时间/nonce 防重放和 ECH 不降级保留。新增单调 `attempt` 放在受认证的 HELLO 内，WELCOME 必须精确回显；服务端在同一 Session 锁内检查和提交新路径。每次激活尝试消耗新序号，准备不消耗；重复、较小或试图用 legacy 零序号替换已经受保护的会话都被拒绝。计数不允许绕回。

本地 `generation` 同样保护帧处理：检查旧 carrier 与修改 Flow 的 DATA/ACK/FIN/RESET/OPEN 状态处于同一临界区。旧路径已出队的帧不能在新路径发布后改变会话。恢复复用原目标 socket，按累计字节偏移重发和去重；不自动重试未知应用请求。

仍有分布式不确定窗口：服务端写出 WELCOME 后可以已经替换旧路径，客户端却没收到 WELCOME。更高 attempt 能继续恢复，旧 attempt 不能再回滚；这不等于原子两端提交，也不能宣称激活失败完全不影响旧路径。只有准备阶段具备“不发送 HELLO、不替换 Session”的保证。原服务进程消失、TTL 到期、目标 socket 消失时旧流明确终止。

`adaptive` 要求新服务端支持 attempt 回显；与原 v0.2 服务端互通须显式保留 `legacy`，不静默放弃已要求的 fence 或 ECH。没有自动 ECH 配置分发/轮换；没有新增公开 CA 或浏览器拟态。详细回归与边界见 [独立复核](review-recovery-v03.md)。

## 机制二：利用窗口余量合并累计 ACK

实现为 `ack_coalesce`，不改变线格式。新 DATA 可以立即交付应用，回复 DATA 也不等待累计 ACK。只有冗余累计 ACK 可等待：无 RTT 样本时最多 5 ms；有样本时使用 `clamp(RTT/4, 1ms, 10ms)`。未确认接收量达到窗口四分之一、应用释放四分之一窗口信用、FIN、重复/缺口数据或新代次恢复时立即可发送 ACK。

它利用了内层累计偏移和有限保留窗口：外层 H2/H3 已负责可靠传输，没有必要把每个 2048 字节 DATA 都变成一个独立即时回执。代价是发送端较晚释放部分已确认缓存，且极低容量/强背压时实际 ACK 排队可能超过计时值。它是有明确限界的 ACK 合并策略，不宣称发明了 delayed ACK；是否改善本代理的包数、延迟和识别问题，由同二进制的开/关消融判断。

新建配置默认 `web_padding=0`：旧随机填充已有可重复成本，却未在本轮留出检测任务中显示收益。显式指定 127 的旧配置保持其设置。`ack_coalesce` 暂保持可选，`recovery_mode` 未指定时保留 legacy 互通；科研参数不能冒充已经验证的通用最优默认值。

## 最终同条件恢复结果

最终冻结程序的联合配置是 `adaptive + count history + causal progress + ack_coalesce + padding0`；v0.2 使用干净 `e4c93d9` 原配置（padding127）。两者共用真实 Linux IP 包链路，8/2 Mbps、100 ms 名义 RTT、相同应用期限与负载，接收端 INPUT 注入 8 秒 UDP 静默黑洞，每种三次配对种子。结果来自 [最终黑洞矩阵](../results/net-v03-joint-blackhole-20261110/analysis-final.json)：

| 指标 | v0.2 | v0.3 联合配置 |
| --- | ---: | ---: |
| 故障开始→客户端承载附着，中位数（范围） | 2859 ms（2851–2862） | 459 ms（436–504） |
| 每会话 SSE 最大间隔的中位数 | 3612 ms | 579 ms（505–660） |
| HTTP 成功 / 总请求 | 223/240 | 237/240 |
| HTTP 超时 / 其他失败 / 结束删失 | 12 / 0 / 5 | 0 / 0 / 3 |
| 原 SSE 目标连接连续 | 0/3 | 3/3 |
| 原 echo 目标连接连续 | 0/3 | 3/3 |
| 每轮 qdisc 帧字节中位数 | 6,101,976 | 5,726,779 |

字节是实测 veth Ethernet 帧计数，不含 FCS；经固定大小 UDP 包校准，不能称为纯 IP 字节。两种承载、握手、填充和备用都经过同一限速链路。表中帧字节为整个测量窗口总量，业务完成数不同，不能直接解释为每单位有效载荷开销。最终新实验使用持久 TCP echo，并未重新运行真实 SSH；历史 SSH 记录单独保留。表中是联合配置对照：填充、ACK、检测、准备及其交互都变了，不能把全额收益归因于单一机制。相同 padding127 的先前恢复消融、独立 ACK 批次与最终 causal/probe-only 对照分别隔离部分原因，详见 [完整实验报告](recovery-lab-v03.md)。三次重复仍不足以证明广泛网络下的尾部保证。

最终关键路径以接收端规则安装开始为零点：故障→怀疑 115–185 ms；备用 TCP/TLS/ECH 准备 213–215 ms，与等待确认同时进行；提交→附着 105–106 ms；附着→首个会话协议进展 102 ms。后者可能是 OPEN/OPENED，不等同于完整 HTTP 响应。故障→首个协议进展为 538–606 ms；保证在注入完成之后新发的受控 POST 到源站约 980–1064 ms，另包含请求发行节拍与流建立。规则安装本身占 38–51 ms，因此不是精确到 1 ms 的物理断链时间。不能把重叠的准备和确认等待重复相加。

最终健康链路另各完成一次：两者 HTTP 79/80，余下一个结束删失，无失败/超时、准备或切换；echo 159/159，有效下载速率均约 1.88 Mbps。联合配置 HTTP p95 208.7 ms、v0.2 210.9 ms，SSE 最大间隔反而为 65.1 vs 56.5 ms；单次不能作尾延迟改善结论。总帧字节 5,653,993 vs 6,448,407（−12.32%）；联合配置客户端/服务端 CPU 均值约 5.31%/4.93% 单核，RSS 峰值约 16.0/18.2 MiB。这只是短测，不是长期资源保证。见 [最终健康及黑洞汇总](../results/net-v03-joint-healthy-20261110/analysis-final.json)。

新的因果进展单独比较共 20 次（两变体 × 健康/高 RTT/双向黑洞/上行黑洞/200 ms pulse × 两种子），双方 HTTP 均零超时、零失败，原 SSE/echo 全部保持目标连接。新机制实际产生 2429 条进展证据；上行黑洞仍从 H3 恢复，没有被下行 DATA 或旧 ACK 永久掩盖。但是 causal 双向黑洞附着 1105/1642 ms，probe-only 为 519/1000 ms；故障前阈值分别为 419/674 ms 和 150/405 ms，RTT 历史并不相同，不能只按开关归因。pulse 中 causal 切换 2/2、probe-only 0/2，SSE 间隔则分别为 382–397 ms 与 417–452 ms。它呈现了额外切换与较短停顿的取舍，**没有证明实测误切率下降**。trace 中新增日志的运行成本也未单独消融。固定输入状态测试只证明因果证据的保守判定，不提供真实误判概率。

此前固定 400 ms 的简单回退在 500 ms 名义 RTT 下出现 0/80 HTTP 成功及反复切换；自适应方案没有出现这类崩溃。参考 Hysteria2.13.0 BBR standard 在本次配置没有 TCP 备用，UDP 黑洞导致重连；Xray26.10.31 REALITY/Vision 使用 TCP，未受该 UDP 故障影响。它们都是有意义的条件性对照，不构成 PROTO-X 普遍更优的证据。

## 抗识别结论与剩余问题

观察者可见性审计、填充预算曲线、独立 ACK 批次及检测定义见 [识别研究](recognition-v03.md)。已加密 H2/H3 字段不冒充沿途可见特征；TLS 1.3 证书消息的纯被动可见性也与主动证书枚举分开。实验中的 native 参照是指定 Go H3 流式应用，不是浏览器总体，也不是未知 DPI。

目的 IP、outer SNI/ECH 使用、外层握手实现、连接关系、包数、方向和时序仍有区分力。单 VPS/私有 CA/共享 SAN/静态 ECH 配置不构成大型匿名集。填充仅改变加密 body 长度，无法自动消除额外往返和控制小包。

本轮不宣称优于所有 VLESS/REALITY/Vision 或 Hysteria2，也不把某协议没有备用路径造成的黑洞失败算成同条件胜利。有限样本低 FPR 结果不能外推百万流量规模。真实俄罗斯家宽/移动网络、现场 DPI、跨网络/时段的识别泛化、长期资源行为仍未完成。

下一项最有依据的恢复实验是按活跃负载短期保留备用连接，检验能否省去目前约 214 ms 的准备关键路径，同时把空闲字节、连接关系、资源和误切换代价完整计入；不是默认无限暖备。识别方向则应先减少持续额外控制往返与连接时序差异，用新的留出采集检查收益，再考虑增加填充预算。
